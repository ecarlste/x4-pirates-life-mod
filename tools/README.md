## Running

From PowerShell, in the repo folder:

```powershell
.\tools\unpack-x4.ps1 -Version 9.00
```

If scripts are blocked, run it for the current session only:

```powershell
powershell -ExecutionPolicy Bypass -File .\tools\unpack-x4.ps1 -Version 9.00
```

From WSL:

```bash
powershell.exe -ExecutionPolicy Bypass -File "$(wslpath -w tools/unpack-x4.ps1)" -Version 9.00
```

Run `Get-Help .\tools\unpack-x4.ps1 -Full` for every parameter (`-X4Path`, `-OutRoot`, `-ToolPath`, `-Force`).

## The game lock

X4 runs one game per Windows login, and this repo and the bounty hunter's share the X4 8.00 copy, so a deploy or game run from either waits for any other. Any tool that changes the game folder or starts the game should take the lock the same way:

- **Where:** the file `game.lock` in the X4 install folder (`<X4_PATH>\game.lock`), the folder both repos' configs name.
- **Format:** UTF-8 text, one `key=value` per line, LF endings:

  ```
  token=<unique per holder>
  what=deploy | game-test | <the tool's own word>
  repo=<repo folder name>
  branch=<branch, or ->
  pid=<holder's process id>
  host=wsl | windows | linux
  started=<UTC, 2026-11-11T09:00:00Z>
  heartbeat=<counter> <UTC time>
  ```

  Only `token` and the rule that the file keeps changing matter to the protocol; the rest is for the waiting message.
- **Taking it:** join the line first (see **The line** below), always, even when the line is empty and the lock is free. Only the first in line takes the lock: create the file exclusively (fail if it exists: `CreateNew` in .NET, `set -o noclobber` in bash), write the lines, and only then delete your ticket. If the file exists, someone holds it: wait, polling every few seconds.
- **Holding it:** rewrite the file (bump the `heartbeat` line) at least every 10 s, and stop if its `token` is no longer yours.
- **Rewriting it, or a ticket:** write the lines to a file beside it and rename that over it, so a waiter reading it never finds a rewrite empty or half-written and names a blank holder. (A lock or ticket is still empty between its exclusive create and its first lines; a waiter names an empty lock as such.) Both `game-lock.sh` and `game-lock.ps1` do this. Rename in one step that replaces the file (`mv -f`, `File.Move` with overwrite, `MoveFileEx`); .NET's `File.Replace` leaves a moment with no file, where a waiter could take the lock. On Windows, the rename fails while a reader has the file open, so a failed ticket or heartbeat rewrite waits for the next poll or beat. The first lines after taking the lock can't wait for that: `game-lock.sh` and `game-lock.ps1` both retry them every 20 ms for about a second, then fail the run. (A Windows reader blocks the rename from WSL too: `mv -f` onto drvfs fails with "Permission denied" while one has the file open.) The empty lock the run leaves goes stale and the next in line takes it over. A reader on Windows can't open the file during the rename either, so `game-lock.ps1` tries a few times before calling it unreadable. A run killed between the two steps leaves a `<name>.<pid>.tmp` beside it; it isn't a ticket, so nothing reads it, and it can be deleted.
- **A crashed holder:** a lock whose text hasn't changed for 60 s, as watched by the first in line on its own clock (so the two clocks never need to agree), is taken over: re-read it, and if it's still the same text, delete it and take it as above. Only the first in line takes over a lock. An empty lock file, or one with no `token` (a crashed or interrupted write), counts the same way; a missing file doesn't, so a holder that has just created the file isn't mistaken for one.
- **Letting go:** delete the file, but only if its `token` is still yours.
- **Handing it down:** a holder that starts another tool which takes the lock passes its token in `X4_GAME_LOCK_TOKEN` (from WSL to a Windows program, list it in `WSLENV` too). A tool whose `X4_GAME_LOCK_TOKEN` matches the file's `token` goes ahead without joining the line, and leaves the file for the holder to delete. It's only for tools nested in one run: chained runs each rejoin the back of the line.
- **Settings** (environment only):
  - `X4_GAME_LOCK_WAIT`: seconds to wait in line. Unset or empty means no limit (the default), since the line is fair. `0` refuses at once if the lock is held or anyone is in line, naming both.
  - `X4_GAME_LOCK_STALE` (default 60): how long a lock or ticket may go unchanged before it counts as crashed.
  - `X4_GAME_LOCK_POLL` (default 5): seconds between checks while waiting.

### The line

Waiters take the lock in the order they arrived, so a session that chains runs back to back can't keep the others out. `make game-queue` shows the holder and the line, with ages.

- **Where:** the folder `game.queue` beside `game.lock`. Whoever needs it first creates it, and nobody removes it.
- **A ticket** is a file in it named by a zero-padded number (`000042`), so the names sort in line order. Its text is the same `key=value` lines as the lock's, for the messages.
- **Joining:** list the line, take the highest number plus one (`1` when it's empty), and create that file exclusively. If the number is taken, try again with the next. Numbers aren't times, so no clocks are compared, and they restart once the line empties.
- **Staying in line:** rewrite your ticket (bump its `heartbeat`) on every poll. Watch only the tickets ahead of yours, and drop one whose text hasn't changed for `X4_GAME_LOCK_STALE` on your own clock: its waiter crashed. Re-read it right before deleting it, as with the lock.
- **Your turn:** with no ticket ahead of yours, you're first in line: take the lock or, if it's crashed, take it over (above).
- **Leaving:** delete your ticket when you take the lock, give up, fail or are interrupted (a `trap` on EXIT in bash, a `finally` in PowerShell).
- **Messages:** while waiting, say your place, who's ahead and who holds the lock, reprinted when that changes: `Waiting for the game lock: 2nd in line, behind <waiter>; held by <holder>`. On taking the lock with others in line: `N waiting behind you; keep this run short`.

### Limits

- **It's per install, not per machine.** It serializes everything that names the same `X4_PATH`, which today is every deploy and game run in both repos (the 8.00 copy). A tool pointed at another install (the 9.00 Steam copy, say) takes a different lock; X4's own one-game-per-login rule and the runner's process check stop the second game from starting, but not the deploy into it.
- It doesn't cover a game started by hand (the runner refuses while `X4` or `X4_nonsteam` runs).
- `X4_GAME_LOCK_STALE` must be the same in both repos: a holder beats every STALE/6 s, so a waiter with a smaller value could take over a live lock.
- Only the first in line takes over a crashed lock, so two queued waiters can't both take it over. A taker from before the line (a worktree branched before it, until it's rebased) still polls the lock directly: it can cut the line, and it could take over a crashed lock at the same moment as the first in line. Each checks the text is unchanged right before deleting it, which makes that window tiny, and at our scale the rest is left to chance.
- The line's order is the order of the ticket numbers, not of arrival to the millisecond: two takers joining at the same moment get the next two numbers in whichever order their creates land.

## Rules

- New tools are TypeScript, run by Node directly (type stripping, no build step; Node 22.18 or later), with Node's built-in test runner: `<tool>.ts` with its modules and `*.test.ts` files in `<tool>/`. `make setup` runs `npm install`; `make test` runs `tsc` and the tests. A worktree uses the main checkout's `node_modules` unless its branch changes `package.json`. The existing Python tools stay Python.
- `tools/standards.test.ts` checks the mechanical rules: only CLIs (`.ts` files using `parseArgs`) sit directly in `tools/`, any other module or test goes in its tool's folder (except `standards.test.ts` itself, which checks `tools/` as a whole); every file directly in `tools/` has a row in the table above, and every row names a file that exists; CLIs read arguments with `parseArgs`, never `process.argv`, and exit 2 with a `Usage:` line on stderr for an unknown option; devDependencies use `^` ranges (`package-lock.json` pins).
- Python tools are named with underscores (`check_test_plan.py`), so their unit tests in `tests/python/` can import them; shell and PowerShell scripts use hyphens.
