# Testing

How to run, add and wire up tests. The scripts say how they fetch and pin their tools: [`tests/run.sh`](../tests/run.sh), [`tests/run.ps1`](../tests/run.ps1), [`.github/test-filters.json`](../.github/test-filters.json), [`.github/workflows/tests.yml`](../.github/workflows/tests.yml) and [`tools/README.md`](../tools/README.md). This page only covers what you have to do.

## Before a PR: `make test`

`make test` (or `tests/run.sh`) runs only the suites your changes need, counted since your branch left `origin/main`, uncommitted files included. It takes about 30 s. `make test ALL=1` (`tests/run.sh --all`) runs everything. Keep it fast: it's meant to run often. Its last line is the result (except with `--lua-only` or `--typescript-only`, which run one suite), `All suites passed` or `FAILED: <suites>`, so reading a run through `tail` is enough.

- **One kind of suite:** `tests/run.sh --lua-only` or `--typescript-only`. `.\tests\run.ps1` runs only the Pester suites (`-Path <file>` for one file, `-Name <pattern>` for matching tests, `-Repeat <n>` for [flaky tests](#flaky-tests)). `tests/run.sh --windows-powershell` runs them in Windows PowerShell 5.1 from WSL (serial, about 4 minutes).
- **One-time installs in WSL:** `sudo apt install parallel libicu78 luajit`. GNU parallel makes bats faster and LuaJIT runs the Lua tests. ICU is optional, since the tests pass without it. The rest gets fetched on the first run.
- CI runs the suites each PR needs, and all of them on pushes to `main`.

## Wiring a test in

- **Test filters:** [`.github/test-filters.json`](../.github/test-filters.json) says which suite depends on which files. It uses [dorny/paths-filter](https://github.com/dorny/paths-filter)'s format, which CI reads through that action and `make test` through `tools/select_tests.py`. Every file in the repo must match a filter (`none` for files that need no test), and every test file needs a filter of its own. The `pick tests` CI job and a Python unit test check both rules.
- **Every script change needs a test.** `deploy.sh` and `deploy.ps1` share one behavior spec, so a case added to `tests/deploy.bats` also goes in one of the `tests/Deploy*.Tests.ps1` files.
- **Pester:** each `tests/*.Tests.ps1` file runs in its own process, all at once. Keep each file under about 20 s, and split it by topic if it grows past that (as `Deploy*.Tests.ps1` does).
- **Lua:** luacheck lints the test extension's Lua and `tests/lua/`. When a file starts using an X4 global, add it to `.luacheckrc`. LuaUnit tests are `tests/lua/test_*.lua`, run under LuaJIT, which is the Lua X4 runs.
- **TypeScript tools** (`tools/`, Node 22.18 or later, packages from `make setup`): tests are `tools/**/*.test.ts`.
- **Python tools** in `tools/` are named with underscores (`check_test_plan.py`), so their unit tests in `tests/python/test_*.py` can import them. The tests use the standard library's `unittest`. The tools' bats tests stay as the end-to-end layer.
- **Diff-patch check** (`tools/check-diff-patches.ts`): it checks every diff patch's selectors against the unpacked 8.00 and SWI files (`X4_UNPACKED` and `SWI_UNPACKED` in `deploy.config`), and skips with a note when they're missing, as it does in CI.
- **Lowercase-paths check** (`tools/check-lowercase-paths.ts`): it runs with the TypeScript tools and fails when a shipped path (an entry in `deploy.include`, or anything under one) has an uppercase letter. A new `deploy.include` entry needs a matching glob in the `typescript` filter; a test fails until it has one.
- **Debug-tags check** (`tools/check-debug-tags.ts`, run with the TypeScript tools): it fails on a probe log tag (`[DEBUG-<id>]`, from `/mattpocock-skills:diagnosing-bugs`) left in `aiscripts/`, `md/`, `libraries/`, `t/` or `tests/game/`, naming each file and line. Remove the probes once the bug is found.
- **Doc-size check** (`tools/check-doc-size.ts`, run with the TypeScript tools): it fails when `docs/PROJECT.md` goes over its size budget (set in the script). Move detail into a doc listed in PROJECT.md's "Where to look" table rather than raising the budget.
- **Doc-paths check** (`tools/check-doc-paths.ts`, also `make doc-paths`): it runs on every change and fails when a doc names a repo path that doesn't exist. Its filter is `**`, which doesn't count as covering a file. Add a rule in `tools/check-doc-paths/paths.ts` only for text that isn't a repo path.
- **Doc-names check** (`tools/check-doc-names.ts`, also `make doc-names`): it runs on every change and fails when a doc or tool names a mod global (`$APiratesLife_…`) that `md/` and `aiscripts/` don't have, or a game test that was removed (found in the harness's and runner's git history, so it fails in a shallow clone). To keep a removed name as history, say "9.x line" or link the issue that removed it on the same line. Research notes, rejected ideas, `DESIGN.md` and `IMPLEMENTATION_PLAN.md` aren't checked.

## Flaky tests

A test that fails once and passes on a rerun is a bug, in the test or the code under it.

- **Log it:** open an issue with the run and job IDs before or right after rerunning. A rerun replaces what `gh run view --log-failed` shows; the failed attempt's log stays at `gh api repos/ecarlste/x4-pirates-life-mod/actions/jobs/<job-id>/logs --allow-escape-sequences`.
- **Measure it:** for a game test, `make game-test RUNNER_ARGS="-Test <name> -Repeat 20"`, split into runs that fit the hold budget (see [Game tests](#game-tests)). For Pester, `.\tests\run.ps1 -Path <file> -Name '<pattern>' -Repeat 50` runs one Pester test 50 times and counts the failed runs. From WSL, run it in Windows PowerShell 5.1 with `powershell.exe -NoProfile -ExecutionPolicy Bypass -File "$(wslpath -w tests/run.ps1)" …`, or in PowerShell 7 with `.tools/powershell-*/pwsh -NoProfile -File tests/run.ps1 …`. Several copies at once add load. If it stays green, widen the suspect timing window with a temporary sleep until it goes red, then fix the cause and show the rate before and after in the PR.
- **Make timing testable:** a script that polls a process or a file keeps that loop in a function a test can drive with a fake process or file (as `Watch-GameRun` in `tools/run-game-tests.ps1`), so its timing is tested every run instead of by luck.

## Test pyramid

Put each test at the lowest level that can prove the scenario:

1. Unit tests (LuaUnit in `tests/lua/`, Python in `tests/python/`)
2. UI tests (the same, with X4's menus stubbed; none on `main`, the settings page's are on `9.x`)
3. Game tests on the `apirateslife_test` start (`make game-test`)
4. By hand

MD and AI scripts only run inside X4, so what they do can't be tested below game tests. The goal is no manual UAT for releases, with a full CI/CD pipeline: by-hand scenarios are debt to drive to zero, and faster tests are better.

## Game tests

`make game-test` first runs the runner's setup checks (`-PreflightOnly`: the executable exists, `X4_PROFILE_ID` is numeric, SWI is installed and on in the test profile with our extensions, no X4 running), so a bad setup stops before anything is deployed. It then deploys the working tree, and `tools/run-game-tests.ps1` starts the X4 8.00 copy's `X4_nonsteam.exe` directly (no Steam), muted (`-disablesound`), in its own test profile, with the dev-only test extension (`tests/game/apirateslife_tests`). The extension runs scripted scenarios in game and quits, and the runner reads the profile's `debuglog.txt` and reports PASS or FAIL. Every run is SWI-only: the runner switches off, in the test profile, every extension installed in the game folder apart from Egosoft's DLCs, SWI and ours. The runner also checks the log itself: `load_order_after_swi`, `clean_log` and `swi_only_run` (the release scenarios) are named in `New-LogCheck` calls in the runner, which `tools/check_test_plan.py` reads as game tests. Profile IDs and paths are in [environment.md](environment.md#paths-eriks-machine).

- **First run:** `make game-test RUNNER_ARGS=-PrepareProfile` makes the test profile from the root profile's settings and switches on SWI, `apirateslife` and `apirateslife_tests`. Without that, the runner refuses to start. It also refuses while `X4` or `X4_nonsteam` is running.
- **The game lock:** it waits while another deploy or game run, from this repo or the bounty hunter's, holds the lock, and waiters take it in the order they arrived ([how it works](../tools/README.md#the-game-lock)). `make game-queue` shows the holder and the line.
- **Keep each hold short:** hold the game for about one PR-tier run (about 5 minutes), so a PR waiting to ship gets the game soon. Split a longer batch (a long `-Repeat`) into runs of about that length, each of which rejoins the back of the line, so others get the game between them. Split it even when `make game-queue` shows nobody waiting: others arrive mid-hold. In [#216](https://github.com/ecarlste/x4-pirates-life-mod/issues/216) a batch started on an empty queue held the game for 25 min 49 s while four sessions queued behind it. That's worth each split's cost of about 55 s of game start ([#195](https://github.com/ecarlste/x4-pirates-life-mod/issues/195)). The runner enforces this for a selection (`-Test` or `-Repeat`) ([#271](https://github.com/ecarlste/x4-pirates-life-mod/issues/271)). Before `make game-test` queues for the lock, the runner works out the selection's worst case: 55 s of game start plus each test run's `<Name>_Timeout` delay, at 1× for a combat test and a sixth of it for the rest, under SETA. It refuses a selection over 5 minutes and says how the worst case adds up. A test that reports from its own actions counts nothing, and one with no timeout cue counts the whole 5 minutes, so give a slow test a timeout cue. One test run is never refused, and whole tiers and `-Release` aren't checked. To take a long hold on purpose, add `-LongHold` to `RUNNER_ARGS`. To keep a split batch's traces together, give its runs one `-RunsLabel` and add `-RunsAppend` to each after the first (see Each run's trace below). `make game-proof` splits a batch and does both for you (see Rates, not single runs).
- **Windows only**, and not in CI. Add a game test with each feature. List it in `$Tests` in the harness, one test per line; `tests/python/test_game_tests_list.py` fails on a test cue that isn't listed. A test too slow for the PR tier goes in `$ReleaseOnly` too ([Game test tiers](#game-test-tiers)).
- **Cue timing:** before timing a test's cues, read MD's cue lifecycle in [research/automated-game-testing.md, First runs in game](research/automated-game-testing.md#first-runs-in-game): sub-cues start when the parent's conditions are met, not after its `delay`, and a sub-cue's delay counts from the parent's activation. In [#216](https://github.com/ecarlste/x4-pirates-life-mod/issues/216) a change was reverted on a wrong belief about when sub-cues start.
- **Debug code in its own commit:** debug instrumentation and probe checks (`[DEBUG-*]`-tagged code, throwaway check cues and their loadouts) go in a commit of their own, apart from changes meant to ship, so a rebase can drop it or resolve it alone. In [#216](https://github.com/ecarlste/x4-pirates-life-mod/issues/216) one WIP commit held both: a rebase conflict took the test files from `main` whole, and `NextTest`'s escape-pod cleanup was lost until the PR review caught it.
- **One test, repeated:** `make game-test RUNNER_ARGS="-Test capture_escaped -Repeat 20"` runs only that test (cue name or reported name, comma-separated for more, run in the order given, release-only ones too), 20 times in one game session, and tallies its failures. `-Repeat` without `-Test` repeats the tier's tests. `ConfigAppliedOnStart` checks the game as it starts, so a selection runs it once, first. It rewrites `$Tests` in the installed copy only, and the harness's `NextTest` resets a test cue that already ran. Every run after the first starts from whatever the one before left behind, unlike the suite.
- **Each run's trace:** the runner writes each test run's `[apirateslife]` and `[apirateslife-test]` lines to `tests/game/runs/<test>-<n>.log` (gitignored), replacing the last run's. A run's lines start after the previous test's result, so a test's cleanup lines land in the next run's file. `node tools/summarize-game-runs.ts` prints one line per run: the time to the bail gates, the lowest hull, knock-downs, the longest stretch at full shields and the finisher's passes, each a hit or a miss ([tools/README.md, Tools](../tools/README.md#tools)). Turn on the capture order's debug lines (`global.$APiratesLife_CaptureDebug`, as the wing tests do) for the passes. `--totals` adds a block per test across the runs: runs and passes, the finisher's hits split by the target's shields at the pass's start, the lowest hull (min and p50), the time to the gates (p50 and p90), the gun swaps and the combat trace's bands summed. `RUNNER_ARGS="-RunsLabel base-b"` keeps a batch's traces in `tests/game/runs/base-b/` instead, replacing only that label's, so batches sit side by side; name a folder to sum up just that batch. Add `-RunsAppend` to keep the label's traces and number the new runs on from each test's highest there, so a batch split into several runs adds up as one.
- **Comparing order variants:** give each variant its own worktree, with its edits left uncommitted as throwaway, and run `make game-test RUNNER_ARGS="-Test <test> -Repeat <n> -RunsLabel <variant>"` in each. Split a batch over the [hold budget](#game-tests) into runs with the same label: the first as above, which clears the label's last traces, and the rest with `-RunsAppend` added, so the label's folder adds up as one batch. Each deploys its own tree when its batch gets the game lock, so the batches can queue side by side; don't edit a worktree while its batch is still queued. Then `node tools/summarize-game-runs.ts --totals <worktree>/tests/game/runs/<variant> …` sums each up, named by folder. That's how [#224](https://github.com/ecarlste/x4-pirates-life-mod/issues/224) compared `finishguns` 1 with the finisher on vanilla's attack.
- **Rates, not single runs:** some outcomes are a rate, not a rule: a capture wing should hold the prize between the gate and the floor in at least 90% of runs ([capture-operation.md](specs/capture-operation.md#design), [#184](https://github.com/ecarlste/x4-pirates-life-mod/issues/184)). Those game tests fail only on what must hold in every run (no kill, no hull below the floor) and report the rest, such as the lowest hull. Each PR runs the PR tier ([Game test tiers](#game-test-tiers)); long batches are optional evidence on PRs that change fire control. Until a Windows CI runner exists, the release checklist has a "90% per wing setup" scenario (`@manual` in `capture-operation.feature`): 40 runs of each wing test before every release, split into holds within the [hold budget](#game-tests) or taken in one with `-LongHold`.
  - **A proof runs with `make game-proof`:** `make game-proof TEST=capture_wing_bails_phantom,capture_wing_breaks_full_shields RUNS=40 LABEL=<batch>` runs 40 runs of each as several `make game-test` calls, each rejoining the back of the line ([#279](https://github.com/ecarlste/x4-pirates-life-mod/issues/279)). It sizes each call within the hold budget from the runner's own worst-case estimates (`-HoldEstimateOnly`, the numbers the hold check uses), so none is refused. A test whose one run is over the budget (a 300 s timeout, say) runs one run per call, and the output calls it a long hold. The first call clears `tests/game/runs/<batch>/` and the rest add to it (`-RunsAppend`), so `node tools/summarize-game-runs.ts --totals tests/game/runs/<batch>` sums the whole proof. It prints a line per call as it finishes (runs passed and failed, outcomes met and missed) and stops at a call with a failed run, since a missed outcome isn't one; `KEEP_GOING=1` runs on. It stays until the wing tests report a split verdict and are in `$ReleaseRuns` ([Game test tiers](#game-test-tiers)).
- **Combat tests run at 1×:** the suite runs under SETA at 6× (the harness's `Begin`, and `KeepSeta` switches it back on when something drops it), which is fine for tests that only wait on travel. A **combat test** is one whose pass, fail or numbers depend on damage landing, such as the capture wing tests. SETA cuts the hits that land: in [#216](https://github.com/ecarlste/x4-pirates-life-mod/issues/216) nose-on fire at 600–1400 m landed damage in 32% of seconds at 6×, against 97–100% at 1×, and players fight at 1×, since the game stops SETA with enemies nearby. So a combat test runs the harness's `MarkCombatTest` as its first action: SETA goes off, `KeepSeta` leaves it off, and `Report` turns it back on. While a combat test runs, `KeepSetaOff` switches SETA off again whenever it finds it on, and logs `SETA came on in a combat test`: a test that starts in the same second `Begin` switches SETA on (the first test of a `-Test` run) saw it come back on about 2 s after `MarkCombatTest` switched it off, and ran at 6× ([#272](https://github.com/ecarlste/x4-pirates-life-mod/issues/272): the first run of each session bailed in 0 of 5, the second in 5 of 5). SETA still reads as on for about 2 s after a toggle, so `KeepSetaOff` waits 3 s after the last one before toggling again. `tests/python/test_game_tests_list.py` fails on a test that marks itself anywhere but first. Tests that force a bail or set the hull by script aren't combat tests, and neither are `NoMissilesInSight` and `NoMissilesOutOfSight`: they're real fights, but they pass or fail on missiles fired, and their target can't drop below 50% hull. When SETA drops after a combat test because enemies are still near, `KeepSeta` switches it back on and the report counts that as a drop.
- **The combat trace:** a dev-only measure of how well wingmen land damage, so combat rechecks measure the same things and their numbers compare ([#220](https://github.com/ecarlste/x4-pirates-life-mod/issues/220)). It's off unless a test runs `CombatTraceStart` (its wingmen, its target) once the fight starts, and `CombatTraceStop` (the test's reported name) before it reports; a test without it logs nothing extra. `CaptureWingHoldsFire`, `CaptureWingHoldsFireThreeWingmen`, `CaptureWingKnocksShieldsAgain`, `CaptureWingBreaksFullShields`, `CaptureWingTurretsHold`, `CaptureWingTurretsHoldM` and the turret damage tests (`TurretDamageSetup`) have it on. The summary in the test's run trace is one line per wingman, then one line on the damage:

  `[apirateslife-test] combat trace capture_wing_knocks_shields_again, wingman 1 of 1: 113 s, shots 101, overheats 0; seconds with its damage/fired/in band, by nose angle and distance: 0-3 deg under 600 m 0/1/2, 0-3 deg 600-1400 m 0/0/3, 0-3 deg 1400 m+ 0/0/3, 3-20 deg under 600 m 4/13/16, 3-20 deg 600-1400 m 0/0/0, 3-20 deg 1400 m+ 0/0/0, over 20 deg under 600 m 3/8/72, over 20 deg 600-1400 m 0/0/14, over 20 deg 1400 m+ 0/0/3`

  `[apirateslife-test] combat trace capture_wing_knocks_shields_again, damage: 10 s with damage, 7 credited to a wingman, 3 unattributed (3 with no wingman named, 0 with more than one)`

  - **Seconds and shots:** seconds the trace ran while the target was operational (the same on every line); the wingman's shots from its lasers and turrets (`event_weapon_fired` events, which may be fewer than bolts); its weapon overheats. Wingmen are numbered in the order the test passed them.
  - **The nine bands:** each wingman's every second goes in one, by its nose angle to the target (0-3, 3-20 or over 20 degrees) and its distance (under 600 m, 600-1400 m, 1400 m or more). Each band gives three counts: the seconds with damage credited to the wingman, the seconds it fired, and all its seconds there.
  - **Damage landed** is a drop in the target's shields plus hull over the second. Shields regrowing in the same second can hide a small hit.
  - **Whose damage:** each second with damage is credited to the one wingman that an `event_player_owned_attacked_object` notice on the target named in that second, or is unattributed: no wingman named (a wingman destroyed in that second doesn't count), or more than one ([#231](https://github.com/ecarlste/x4-pirates-life-mod/issues/231)). The notices aren't one per bolt ([#216](https://github.com/ecarlste/x4-pirates-life-mod/issues/216)), but they name a wingman in most seconds with damage: 13 of 17 over six one-wingman runs, none naming two. A notice that arrives a second late credits the next second instead: with one wingman that shows only as an unattributed second, but with several it could credit the wrong one, and no count shows it. No per-hit event names the shooter: the target's shield and hull damage events don't, and its `lastattacker` changes only with these notices. The damage line gives the seconds with damage, how many were credited and how many weren't, so a reader sees how much the per-wingman counts cover.
- **Reporting:** `make game-test-report` posts the report to your PR as a comment and a `game-tests` check. It works only if the run was on the PR's latest pushed commit, with nothing uncommitted, and was the whole suite of a tier (no `-Test` or `-Repeat`).
- Background: [research/automated-game-testing.md](research/automated-game-testing.md).

### Game test tiers

| Tier | Command | Runs | Budget | When |
| --- | --- | --- | --- | --- |
| PR | `make game-test` | `$Tests` but `$ReleaseOnly` | 5 minutes | Required for a PR |
| Release | `make game-test RELEASE=1` | All of `$Tests`, each `$ReleaseRuns` test N times | 30 minutes | Before a release |

- **The budget** is the runner's run from the game's launch to its quit, after the setup checks, the deploy and any wait for the game lock. The report shows the run's length and the tier, and warns, without failing, when a run is over its tier's budget. Over the PR tier's budget is the signal to move a slow test to `$ReleaseOnly`.
- **`$ReleaseOnly`** sits next to `$Tests` in the harness's `Run` cue, one test per line like `$Tests`, or `[]` when empty. Every name in it must be in `$Tests` too: `tests/python/test_game_tests_list.py` fails on one that isn't. The runner leaves those tests out of the installed copy's `$Tests` on a PR-tier run (`-ReleaseTier` keeps them).
- **`$ReleaseRuns`** gives a test with a rate (see [Rates, not single runs](#game-tests)) its runs and the passes it needs, one entry per line as `[<test>, <runs>, <passes needed>]`, or `[]` when empty. The PR tier runs it once; the release tier runs it N times in a row, where it stands in `$Tests`, and fails it below the bar. The report shows it as "k of N, needs M". For a 90% bar use **10 runs needing 8**: a healthy 90% feature passes 93% of release runs, one that has fallen to 60% passes about one in six. For an 80% bar use **10 needing 6**: an 80% test passes 97% of release runs, one fallen to 50% about three in eight. The release run catches regressions, it doesn't re-prove the bar: the 40-run proof (34 needed for a 90% bar, 30 for 80%) belongs in the PR that changes the tuning behind it: 40 runs, with `make game-proof` (see [Rates, not single runs](#game-tests)) or with `-LongHold`. `tests/python/test_game_tests_list.py` checks the list: every test in `$Tests`, more than one run, and passes needed from 1 to the runs.
- **A split verdict:** a test with a rate reports its invariants and its outcome apart, `table[$name, $ok, $detail, $outcome]` to `Report`. `$ok` is the invariants (never destroyed, hull above the floor, gates reached): a failed one fails the run in either tier. `$outcome` (true or false) is the result it aims for, such as the pilot bailing: it's logged (`PASS <name> outcome=missed: ...`) and never fails a run on its own, so the PR tier stays deterministic. In the release tier a run counts towards its bar only when it passed and met its outcome; a test that reports no outcome counts its passes.
- **Repeats run in one game session**, as `-Repeat` does, not a relaunch per run. A relaunch costs about 50 s (X4 to the main menu, 31–48 s, and the test game's load, about 20 s), against about 1 to 2 minutes for a combat test's run ([#216](https://github.com/ecarlste/x4-pirates-life-mod/issues/216): 80 runs in 143 minutes), so it would add about half again to a release run. The cost is state: each run starts from what the one before left, so a repeated test sets up its own ships and settings rather than relying on a fresh game.
- **One PR-tier test per feature:** a PR can let a slow test's regression onto `main`, and the release run catches it before anything ships. To keep that rare, every feature with a release-tier test keeps at least one PR-tier test of its logic (orders, events, gates), without measuring hit rates. No check enforces this; reviews do.

### Release sessions

Some release scenarios need more than one game: a save made without the mod, loaded with it, and a save made with it, loaded without it. `make game-test RUNNER_ARGS=-Release` runs them in place of the game tests, one X4 start per session, about 5 minutes in all:

1. **Without the mod:** the runner switches the mod and the game tests' extension off in the test profile. The release test extension (`tests/game/apirateslife_release_tests`, dev only, like the game tests' one) starts its own gamestart, a copy of the test gamestart that can be saved, and saves it as `apirateslife_release_1`.
2. **With the mod:** both back on. The release extension loads that save; the harness's `Run` cue starts on the loaded game, with `$Tests` rewritten to the session's tests and the game tests' autostart told to start nothing. The last test, `ReleaseLeftovers`, leaves ships taken, an operation called off and one still running. Once the tests are done the harness asks the release extension to save, as `apirateslife_release_2`, and the game quits.
3. **Without the mod again:** the release extension loads that save and finds what `ReleaseLeftovers` left (`global.$APiratesLifeTest_Leftovers`). It checks the uninstall scenario's list on it, plays 10 minutes under SETA and reports `uninstall_leftovers`.

`existing_save_loads` and `save_plays_without_mod` read the sessions' logs, kept as `debuglog.release-1.txt` to `-3.txt` in the profile, and each session gets the log checks, named for it (`clean_log (session 1)`). Session 3's `clean_log` allows the two errors X4 logs when it can't import the wingman's capture order (`AllowedErrors` in `Get-ReleaseSessions`), and counts them in its detail. The run reports like the game tests, but `make game-test-report` posts it as a `game-tests-release` check. The sessions are in `Get-ReleaseSessions` in the runner, and `tests/python/test_release_gamestart.py` keeps the two gamestarts the same.

## Test plan

`tests/game/features/*.feature` says in Gherkin (Given/When/Then) what each feature should do, one file per feature. Write a feature's scenarios with its spec, before the tests. Nothing executes the feature files; the steps live in the tests. Each scenario's tags say how it's verified:

- **The tests that cover it:** game tests by the name they report (e.g. `@bail_raises_bailed`), and unit tests by their test function's name (e.g. `@test_refuses_default_in_any_case`). Several tests can share a scenario.
- **`@pending`:** no test yet, but one is planned. Checked by hand until then.
- **`@manual`:** checked by hand for now, because automating it is hard (e.g. something surviving an X4 restart). Automation is still wanted.

Tests, `@pending` and `@manual` don't mix on one scenario. `tools/test_plan_docs.py --checklist <file>` writes every scenario still checked by hand as the release checklist.

- **Checks:** `make test` runs `tools/check_test_plan.py`. Every tag must name a game test or unit test, every game test needs a scenario (unit tests may cover details no scenario names), unit test names are unique, and every spec links its feature file. On PRs, `tools/check_test_plan_changes.py` fails when a spec or a game test changed but the plan didn't; the PR description then says `Test plan: no change`. Branch protection on `main` requires this check.
- **Readable test plan:** `docs/test-plan/` has a page per feature and an [index](test-plan/README.md) with the counts per feature, including **By hand** (manual plus pending), the number to drive to zero. Run **`make test-plan`** after changing feature files or tests, and commit the result. Don't edit the pages by hand. `make test` warns when they're out of date, and CI fails the PR.
